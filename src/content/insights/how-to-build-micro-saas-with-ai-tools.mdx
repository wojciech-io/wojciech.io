The apps at [app.wojciech.io](https://app.wojciech.io/apps) were mostly built in 2024–2026. A mix of productivity utilities, niche market tools, and internal operator tools that eventually became public. Some are actively used. Some are experiments I learned from. A few are both.

Here's what I've learned about building this kind of portfolio with AI assistance.

## The micro-app definition

A micro-app solves exactly one problem for a specific person in a specific situation. Not a category of problems. Not a platform. One problem.

- **Działka+**: finds building permit status for Polish land parcels (one query, one answer)
- **Paczka+**: tracks Polish courier deliveries with better notifications than the native apps
- **Resume+**: formats a CV into a clean, ATS-compatible PDF in under 60 seconds
- **NotchCue**: keeps speaker notes near the camera during video calls

Each of these has a description that fits in one sentence because the problem fits in one sentence. When the problem description starts requiring "and also": that's the moment scope has crept past micro-app territory.

## How AI changed the build process

Before AI assistance, shipping a real, deployed tool as a solo operator required either a frontend background or significant help. Shipping a native macOS app as a non-Swift developer was essentially off the table.

AI changed this in specific ways:

**Syntax and boilerplate**: I don't need to know the exact AppKit API for a floating NSPanel. I describe the behavior; the model produces correct Swift. This is the largest unlock for non-native-platform developers.

**Debugging**: "This returns undefined when the array is empty" generates a fix faster than StackOverflow because the fix is contextual to the actual code.

**API integration**: courier tracking APIs, land registry APIs, PDF generation: the integration code that used to require reading 40 pages of documentation can often be scaffolded from a description of the input/output contract.

What AI doesn't change:

**The product decision.** Whether to build this at all. What the exact behavior should be. Where the edge cases matter. What the UI should feel like. These remain human decisions.

**The distribution problem.** Building is now faster. Finding the right users is as hard as it's ever been.

## The scope creep pattern

Every micro-app I've built has had a moment where the temptation to add "just one more thing" appeared. Paczka+ tracking → add a package history view → add a price comparison tool → add crowdsourced delivery speed data.

Each addition is individually reasonable. Together they turn a tool that solved one problem correctly into a tool that solves three problems adequately. The original value: instant, no-friction tracking: gets diluted.

The discipline is: ship the one thing. If users ask for something adjacent, that's a different product.

## What I'd do differently

**Launch earlier.** The instinct is to ship when it's ready. Define "ready" as: does it solve the core problem without breaking? Not: is every edge case handled?

**Charge earlier.** Free apps attract free users who give low-quality feedback. Even a small price filters for people who have the problem seriously enough to pay for the solution.

**Pick distribution before picking the problem.** The apps I built that had an existing distribution channel (SEO-searchable problem, community with the specific need) got used. The apps I built that required me to find the audience myself did not.

## The portfolio value

The apps collectively serve as proof that I can ship real products, not just design systems or advise on GTM strategy. That's worth something independent of any individual app's revenue. For the kinds of engagements I take on: embedded growth operator, AI systems builder: the ability to produce working software is a differentiator.

The portfolio is also a learning substrate. Each app taught me something about user behavior, deployment, pricing, or technology that I've applied in subsequent work. The ROI on the time is higher than any single app's direct output would suggest.
