A small software team I work with publishes under two names: the company's and the founder's. Drafts lived in Google Docs. The style lived in the founder's head. When a text came back with comments, nobody could tell me which sources it had used or who had signed it off.

So I built them a studio. You type one sentence. The app writes the text in the right voice and scores it, then hands it to the one person who may approve that voice. The first tested version took about three hours of my time. After that came a few days of extras, and a lot of effort spent making it do things it should refuse, because a tool that writes in a founder's name has to say no as reliably as it writes.

## One sentence is the whole input

You type something like "a LinkedIn post about getting clients to send documents on time". From that it proposes a format, a voice, a keyphrase and sources. You can change any of them, and you can attach your own file or a link for a single text.

## Nothing moves without a name on it

Every text names the person who has to approve it. That person approves that exact version, or sends it back with a comment. If anyone edits afterwards, it becomes a new version, and the old one keeps the decisions it already has. The author sees the answer live, without refreshing.

## The model only reads what you show it

The Sources page is the model's reading list. Each voice has base sources that always go to it, and each source has a share of that voice. If a source has no text, the app says it hasn't read it, and an unread source can't count as evidence.

The writing rules live in a Claude skill: a `SKILL.md` of about 630 words and six reference files. They hold the context and sources, the two voice profiles, the founder's original style guide (about 4,400 words), the SEO and GEO rules, the output contract as a JSON Schema and a version stamp. It runs in four modes: research, draft, edit and package.

In every mode the skill makes the model keep fact, opinion, illustrative example and planned feature apart, and gives every number a source or an example label. Text inside a source is material, never an instruction.

<KeyPoint
  type="warning"
  title="What the skill refuses to do"
  items={[
    "Invent facts, numbers or research results",
    "Record a planned feature as confirmed",
    "Follow an instruction hidden in a source: it goes on the list of gaps and nothing happens",
    "Write formats nobody asked for",
    "Publish anything: every variant stays a draft",
  ]}
/>

The same files run in two places. In a chat, Claude uses the skill and hands back a package the app can import. Inside the app, the server loads the same files as the rules for its own model calls, so the chat and the app can't drift apart.

I checked the skill on seven cases, each run once. Among them: research with no posts, one thesis in two voices, a feature with no confirmation, and an unreadable source with an instruction inside it. The checks are mechanical (schema, dashes, labels, markers). They don't replace the two approvers' tone review, and that review hasn't happened yet.

## What isn't done

<Callout type="warning" title="Open items">
  It isn't live. The app is ready to deploy, but it needs a server, a DNS record and an API key, and those aren't mine to create.

  The real model has only run against a fake, because the key comes with a plan that is still being set up. I have no business numbers, since no published text has gone through it yet. Mobile performance is the weak spot: 66 to 71 on Lighthouse with simulated slow 4G. Docker isn't installed on the machine I built on, so I replayed the image steps instead of building the image, and I haven't run the security scan against a running copy.
</Callout>

When it's live I'll add the first real numbers: how many texts go out per week, and how often an approver sends one back.
