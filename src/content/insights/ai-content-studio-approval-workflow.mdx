A small software team I work with publishes in two voices: the company's and the founder's. Drafts lived in documents and style lived in people's heads. When a text came back for comments, nobody could tell me which sources it was based on or who had signed it off.

So I built an AI content studio for it. The first working, tested version took about 3 hours of hands-on time. After that came a few days of extras and a lot of trying to break it, because a tool that writes in a founder's name has to refuse things as reliably as it writes them.

## How the skill works

The writing rules live in a Claude skill: a `SKILL.md` of about 630 words and six reference files. They hold the context and sources, the two voice profiles, the founder's original style guide (about 4,400 words), the SEO and GEO rules, the output contract as a JSON Schema and a version stamp. A demo case comes with it.

In its four modes (research, draft, edit and package) the skill makes the model separate fact, opinion, illustrative example and planned feature, give every number a source or an example label, and leave an unreadable source unread. Text inside a source is material, never an instruction.

<KeyPoint
  type="warning"
  title="What the skill refuses to do"
  items={[
    "Invent facts, numbers or research results",
    "Record a planned feature as confirmed",
    "Follow an instruction hidden in a source: it goes on the list of gaps and nothing happens",
    "Write formats nobody asked for",
    "Publish anything: every variant stays a draft",
  ]}
/>

The same files run in two places. In a chat, Claude uses the skill and hands back a package that the app can import. Inside the app, the server loads the same files as the rules for its own model calls, so the chat and the app can't drift apart.

I checked the skill on seven cases, each run once: research with no posts, one thesis in two voices, numbers and example status, a feature with no confirmation, an unconfirmed story and news item, a newsletter for the founder with a teaser for the brand, an unreadable source with an instruction inside it, and a single chosen format. The checks are mechanical (schema, dashes, labels, markers). They don't replace the tone review by the two approvers, and that review hasn't happened yet.

<Accordion
  items={[
    { title: "A contract first", body: "JSON Schemas for the request and for what comes back. Whatever the model returns is checked against them, whether it arrives through the API or someone pastes what Claude wrote in a chat window." },
    { title: "A dull stack", body: "One Node process, Express, SQLite on one disk, React with Vite and Tailwind, and nothing else running next to them.     { title: "Shared logic, written once", body: "Scoring and the rules for links, channels and style sit in one folder that the browser and the server both import. The editor shows a live score, and the server runs the same code before a text can go to approval, so the two can't disagree." },

## What is not done

<Callout type="warning" title="Open items">
  It isn't live. The app is ready to deploy, but it needs a server, a DNS record and an API key, and those aren't mine to create.

  The real model has only run against a fake, because the key comes with a plan that is still being set up. I have no business numbers, since no published text has gone through it yet. Mobile performance is the weak spot: 66 to 71 on Lighthouse with simulated slow 4G. Docker isn't installed on the machine I built on, so I replayed the image steps instead of building the image, and I haven't run the security scan against a running copy.
</Callout>

When it's live I'll add the first real numbers: how many texts go out per week, and how often an approver sends one back.
