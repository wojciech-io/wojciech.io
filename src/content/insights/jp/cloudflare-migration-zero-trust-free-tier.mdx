[前回の記事](/jp/insights/astro-cloudflare-pages-portfolio-ai-workflow)では、このポートフォリオをAstroとCloudflare Pagesで再構築した経緯を取り上げた：スタック、マルチエージェントワークフロー、Terraform設定、デプロイモデル。今回の記事は、プラットフォームに付いてきたものについて書く：多くの人が見落としているセキュリティとアイデンティティのレイヤー。登録した理由ではなかったからだ。

---

## なぜ重要なのか

大半の人はCloudflareをCDNにレジストラが付いたものと考えている。10年前ならその理解で良かった。実際には、プラットフォームは今や無料枠で完全なセキュリティスタックを提供している：マネージドWAF、L3とL7のDDoS対策、Zero Trust Access、Tunnels、WARP、Bot Fight Mode、レート制限。

同等の個別ソリューションを組み合わせるなら：WAFに[Akamai](https://www.akamai.com/)か[Imperva](https://www.imperva.com/)、アイデンティティプロキシに[Okta](https://www.okta.com/)かDuo、トンネルに[Tailscale](https://tailscale.com/)かWireGuard、CDNにCloudflare自体か[Fastly](https://www.fastly.com/)：エンタープライズ枠に達する前に月額数百ドルになる。Cloudflareの無料またはProプランでは、ほとんどが含まれている。

注意点：どれも自動では有効にならない。移行時にこれらの機能へのアクセスを得るが、自分でオンにする必要がある。

## ホスティングとデプロイ

セキュリティスタックの前に基本：Cloudflare Pagesはホスティングレイヤーだ。サイトは静的なAstroビルド。GitHubの`main`ブランチへのプッシュごとにCloudflare側でビルドが走り、グローバルエッジネットワークへデプロイされる。ブランチプッシュは独自のプレビューURLを取得するので、本番環境に到達する前に実際のドメインで変更をレビューできる。

ホスティングをCloudflareに置くことで、DNS、CDN、WAF、Zero Trust Access、デプロイターゲットがすべて同じプラットフォームになり、同じAPIで設定できる。後述するセキュリティスタックに依存するサイトにとって、ホスティングを別のプロバイダーに分けることはエッジを二か所で管理することを意味する。Vercelはフレームワーク重視のアプリケーションにはより強力なプロダクトだ。すでにCloudflareのネットワークを経由している静的サイトには、Pagesがより摩擦の少ない選択肢だ。

## Cloudflare WAFとDDoS

ドメインがCloudflare経由でプロキシされているとき（DNSダッシュボードのオレンジクラウド設定）、L3およびL4 DDoS対策が即座に有効になる。これは設定可能でも任意でもない：プロキシされたすべてのトラフィックに対してデフォルトで有効だ。Cloudflareのネットワークがボリューム攻撃をオリジンに到達する前に吸収する。

レイヤー7 DDoS対策、つまりHTTPフラッド緩和も、マネージドWAFルールを通じて無料枠で利用可能だ。これらは一般的な攻撃シグネチャをカバーする：SQLi、XSS、既知のエクスプロイトパターン、既知の悪意あるアクターのIP範囲。

Bot Fight Modeは既知のボットインフラストラクチャに対してチャレンジを出すワンクリック設定だ。静的ポートフォリオでは実用的な効果は最小限：ブルートフォースするログインフォームもスクレイプするAPIエンドポイントもない。しかし有効にする価値はある：ボットトラフィックはアナリティクスを歪め、帯域幅を消費し、存在しないパスを探索することがある。

無料枠のレート制限は基本的だ：10分あたり最大100,000リクエストのルールひとつ。個人サイトにはこれで現実的な脅威面をカバーできる。高トラフィックアプリケーションにはProプラン以上が必要だ。

知っておくべき挙動がひとつ：Cloudflareダッシュボードから「Block AI bots」を有効にすると、ClaudeBot、GPTBot、Google-Extendedなどに対する`Disallow`ルールを合成robots.txtに挿入し、リポジトリ自身のrobots.txtを上書きする。これが前回の記事で取り上げたAIインデックス問題の原因だった。修正方法：そのトグルを無効にし、リポジトリレベルのrobots.txtにアクセス制御を任せる。

## Zero Trust Access

Cloudflare Accessはアイデンティティプロキシだ。定義した任意のURLの前に座り、リクエストをオリジンに転送する前に認証チェックを強制する。ユーザーはサーバーに直接触れない：まずCloudflareに対して認証する。

実用的なユースケースは内部ツールだ。n8n、Grafana、Supabase Studio、またはステージング環境をプライベートサーバーやVPSで運用している場合、通常2つの選択肢がある：インターネットにポートを開く（悪手）、またはVPNを設定する（保守コスト）。Accessは第3の選択肢だ：ポートを閉じたまま、ホスト名の前にCloudflare Accessポリシーを置き、認証をCloudflareに任せる。

設定は簡単だ：

1. ホスト名をCloudflare DNSに追加する（プロキシ）。
2. Zero TrustダッシュボードでAccessアプリケーションを作成し、ホスト名を指定する。
3. ポリシーを定義する：メールパターン、GitHub Org、またはGoogle Workspaceドメインに一致するユーザーを許可する。
4. URLにアクセスしたユーザーにはCloudflareがホストするログイン画面が表示される。メールOTP、GitHub OAuth、またはGoogleで認証する：自分側でのアカウント作成は不要。

無料枠は最大50ユーザーをサポートする。ほとんどのソロオペレーターや小規模チームのセットアップには十分だ。

特に有用なケース：コントラクターや外部ステークホルダーにステージング環境への一時的なアクセスを与えること。どこにもアカウントを作成せず、ポートを開けず、Slackでクレデンシャルを送信しない。

## Cloudflare Tunnel

Tunnelは別の問題を解決する：ファイアウォールポートを開けずに、ローカルで動作しているサービスをパブリックURLで公開すること。

メカニズムはマシンまたはサーバーからCloudflareのエッジへの永続的なアウトバウンド接続だ。`cloudflared`デーモンがトンネルを確立する。Cloudflareはインバウンドリクエストをトンネル経由でローカルに指定したポートにルーティングする。ホスト側でインバウンドポートを開く必要はない。

<CodeBlock
  lang="bash"
  title="Terminal"
  code={`# cloudflaredをインストールし、次に：
cloudflared tunnel login
cloudflared tunnel create my-tunnel
cloudflared tunnel route dns my-tunnel staging.example.com
cloudflared tunnel run --url http://localhost:3000 my-tunnel`}
  caption="名前付きトンネルはホスト名を永続的に維持する。ngrokの無料枠とは異なる。"
/>

トンネルは永続的だ：ngrokの無料枠のようにセッション終了時に期限切れにならない。ngrokはプロセスが停止するとトンネルを終了し、再起動ごとに新しいURLを割り当てる。名前付きCloudflare Tunnelは同じホスト名を永続的に保持する。

典型的なユースケース：

- **実URLでのローカル開発。** Webhookテスト、OAuthコールバック、またはデプロイサイクルなしでWIPをクライアントと共有。
- **インフラなしのデモ。** アプリをローカルで起動し、パブリックURLを渡し、完了したらトンネルを閉じる。
- **プライベートネットワーク上のセルフホストサービス。** Raspberry PiやホームサーバーでHome Assistant、Jellyfin、またはプライベートAPIを運用する場合、パブリックIPやポートフォワーディングルールなしでクリーンなドメイン経由でアクセス可能にできる。

ngrokと比較して、Cloudflare Tunnelは無料で永続的、帯域制限がなく、Accessポリシーと直接統合できる：つまり2つの設定変更でトンネルの前に認証を置ける。

## WARPとプライベートネットワーク

WARPはCloudflareのデバイスクライアントだ：WireGuardベースのエージェントで、デバイスをCloudflareのZero Trustネットワークに接続する。実質的には軽量なVPN代替として機能する。

Zero Trust内でのユースケース：複数のマシン、開発ワークステーション、ステージングサーバー、ビルドマシンがある場合、各マシンをWARPに登録し、Zero Trustダッシュボードでプライベートネットワーク範囲を定義し、Cloudflareのエッジ経由でマシン間のトラフィックをルーティングできる。どのマシンもパブリックIPや開放ポートが不要だ。

これは完全なメッシュネットワーキングソリューションではない。複雑なサービス間ネットワーキングには[Tailscale](https://tailscale.com)やコーディネーターノード付きWireGuardの方が柔軟だ。しかし、開発者のラップトップがステージングデータベースやプライベートAPIエンドポイントに到達する必要がある小規模セットアップでは、シンプルなネットワークポリシーを持つWARPは10分の設定で、さもなければ保守しなければならないVPNサーバーを置き換える。

## オープンソースの代替

上記で説明したすべてにオープンソースの同等品がある。CaddyとAutheliaがZero Trust Accessと同様の認証プロキシを処理する。WireGuardやTailscaleがWARPやTunnelと同様のプライベートネットワーキングを処理する。Fail2banとModSecurityがWAF的なフィルタリングを処理する。

率直な比較：

| | Cloudflare | オープンソース |
|---|---|---|
| セットアップ時間 | 数分 | 数時間から数日 |
| 運用コスト | ほぼゼロ | 継続的 |
| ベンダーロックイン | 高 | なし |
| 費用 | 無料から低 | インフラコスト |
| 柔軟性 | CFエコシステムのみ | 任意 |

プライバシーとベンダー独立性が制約であるなら、またはサードパーティ経由でルーティングできないインフラを運用しているなら、オープンソースの道が正しい。WireGuardは特に、他に何を使っていても運用する価値がある。プロトコルを理解することは有用だ。

制約が時間と運用コストであるなら、Cloudflareのスタックが実用的に勝つ。専任のops機能を持たないソロオペレーターや小規模チームにとって、トレードオフは明確だ。

## 注意点

このスタックのすべてはCloudflareネイティブだ。

WAFルール、Accessポリシー、Tunnel設定、レート制限ルール：どれもポータブルではない。Cloudflareから移行する場合、移行先のプラットフォームでこれらのレイヤーをゼロから再構築する。Accessポリシーのエクスポートフォーマットも、オープンスタンダードも、WAFルールを他で動かすTerraformプロバイダーも存在しない。

個人サイトや小規模な内部ツールセットにとっては、許容できるトレードオフだ。設定は再構築できるほど単純で、3年から4年にわたる運用コストの削減は大きい。

コンプライアンス要件のある組織や、マルチクラウドポータビリティが必要な組織にとっては、ロックインは実質的なコストだ。Infrastructure-as-Code（CloudflareプロバイダーでのTerraform）は少なくとも設定をバージョン管理してレビュー可能にするが、CloudflareのAPIに対してしか動作しない。

実用的なルール：初日からすべてのCloudflare設定にTerraformを使う。ダッシュボードのみの設定は目に見えないドリフトであり、移行時の負債になる。

## オブザーバビリティ

WAFとDDoS対策はサイトが到達可能で保護されていることを教えてくれる。訪問者のブラウザで実行されているコードがエラーを投げているかどうかは教えてくれない。それは別の関心事であり、Cloudflareはカバーしていない。

wojciech.ioでは、そのレイヤーはSentryだ。Cloudflareのプロダクトではないが、オブザーバビリティはホスティングとセキュリティスタックと自然に組み合わさり、無料枠はこのサイズのサイトには十分だ。SDKはプロダクションビルドでのみ初期化し、未処理のエラーとパフォーマンストレースのサンプルをキャプチャし、完全なスタックトレース付きでダッシュボードに報告する。

<Callout type="tip" title="DSNはシークレットではない">

Sentry DSNはインバウンドイベント用のプロジェクトを識別する：クライアントバンドルに含めるように設計されている。保護が必要なのはソースマップアップロードに使うビルドタイム認証トークンだ：これは環境変数に置くべきで、リポジトリには絶対に含めない。

</Callout>

実用的な価値はシグナル品質だ。静的サイトでは壊れるものが少ないため、Sentryのエラーはバックグラウンドノイズではなく実際のイベントだ。何かが壊れたとき：サードパーティスクリプト、ブラウザ固有のAPI、不良デプロイ：訪問者が報告するのを待つのではなく、スタックトレース付きで表面化する。

## 使っているもの

wojciech.ioで有効なCloudflareスタック：

- **Pages**：本番ホスティング、ブランチプレビュー、カスタムドメイン
- **WAFマネージドルール**：プロキシDNS経由でデフォルト有効
- **Bot Fight Mode**：有効
- **Zero Trust Access**：2つの内部ツールで使用中

予定：ローカル開発アクセス用の永続Tunnel。必要時にngrokを起動する現在のワークフローを置き換える。

Accessの設定は約15分で完了した。WAFとBot Fight Modeはワンクリック。有効化以降の運用コストはゼロ。

## まとめ

Cloudflare Pagesへの移行は主にホスティングの決定だ。しかし付いてくるセキュリティスタック：WAF、DDoS対策、Zero Trust Access、Tunnels：が、留まるための目立たない理由だ。

すでにCloudflareを使っているなら、ほとんどは今すぐ利用可能だ。Bot Fight Modeを有効にし、マネージドWAFルールをオンにし、内部ツールがあるなら基本的なAccessポリシーを設定する。ほとんどが15分で、費用はかからない。
