A small software team I work with publishes in two voices: the company's and the founder's. The drafts lived in documents and the style rules lived in people's heads. When a text came back for comments, nobody could tell me which sources it was based on or who had signed it off, and nobody knew if it still sounded like the founder.

So I built a studio for it. It took two days to get a working, tested app. After that I spent a while trying to break it, because a tool that writes in a founder's name has to refuse things as reliably as it writes them.

## One field and an approver

You type what you want, like "a LinkedIn post about getting clients to send documents on time". From that it works out format, voice, length and a main keyphrase. It picks sources from a library and has Claude write the text (Sonnet 5.5 by default), scores the draft for SEO and GEO, and sends it back to the model up to twice for fixes. Then it lands with the person who approves that voice. Nothing reaches the calendar before they say yes.

## Why two days was enough

The first thing I wrote was the output format. Before there was any interface I had the writing rules as a Claude skill, two JSON schemas (one for the request, one for what comes back) and a demo package: one thesis written five times, in both voices. That package turned into the test fixture, the seed data and my first acceptance example. Whatever the model returns is checked against the schema, whether it arrives through the API or someone pastes what Claude wrote in a chat window.

The stack is dull on purpose. One Node process, Express, SQLite on one disk, React with Vite and Tailwind. No queue and no second service. The team is small and there are a few hundred records, so a backup is a copy of one volume, and the tests can start a real server on a temporary database in about a second. It won't scale out. For a team this size that doesn't matter.

The scoring and the rules for links, channels and style sit in one shared folder that the browser and the server both import. The editor shows a live score, and the server runs the same code before a text can go to approval, so the two can't disagree.

Everything outside the app has a fake in the tests: the model, Google Drive and Docs, GitHub. The whole suite needs no keys and no network and runs in about 70 seconds. The price is that I haven't run the real model yet. More on that at the end.

I also ended each day with a handoff note in the repo, a status file that marks every requirement as done, verified or open, and a list of traps that had already cost me time. Two days is short, and it is still long enough to forget why you did something.

## Working with Claude Code

Claude Code did most of the typing. I decided what "done" meant for each piece and what the app has to refuse to do. It wrote the code and the tests, re-ran everything after every change and produced the audits: accessibility, Lighthouse, a secret scan over the whole git history, a boot in production mode from a clean directory.

I don't trust the model's text by default either. A few mechanical checks run on every draft: a number that is only an example has to be marked as one, and a planned feature can't be recorded as confirmed. After that a person decides.

## Breaking it on purpose

The rules I care about live in code, not in the prompt, and each one has a test. Each voice is its own model call, so the brand call never sees the founder's style or her posts. Only the formats you picked get written, and extras from the model are dropped. A source counts as read only if the app holds its text. The model approves nothing. A retry doesn't create a duplicate. There are smaller ones too. A test fails if a dash of any kind shows up in the code or the texts, and another fails if a font size doesn't come from the design tokens.

A green test proves very little if it can't go red. So I switched off 15 safeguards one at a time, 10 on the first day and 5 in the Google sign-in the day after: domain, nonce, state, verified email and session expiry. Every time, something went red.

The first full run had 85 integration tests and 15 browser tests. By the end of the second day there were 325 and 33. After the deployment files, the attachments and the second voice view it stands at 338 and 40, and they finish in about 70 seconds on a laptop. Lighthouse gives 100 for accessibility and for best practices on every page, axe finds no violations, the production dependencies have no known vulnerabilities, and a secret scan of the whole git history found nothing. I also replayed the Dockerfile steps in a clean directory and booted in production mode. Sign-in redirects to Google with PKCE and the security headers are set. API calls without a session get a 401.

## What broke along the way

Quite a bit. Upgrading React Router fixed an open redirect and broke five browser tests, because version 7 wraps URL updates in a transition and the view updated one frame late. The fix is one prop, and a comment that says why it's there. The first Lighthouse run showed a layout shift of 0.52 on the Sources page on a phone, because the page painted as each query came back. It waits for all its data now and the shift is 0.02.

The library loader skipped a file it should have read, which meant the founder's posts would have been missing on a fresh database. I only found it because I was verifying a fresh start. And I built a spend counter before I understood the problem. The team pays through plan credits, not per call, so what's useful is a clear message when the credits run out. The counter is gone and the message stayed.

## What is not done

It isn't live. The app is ready to deploy, but it needs a server, a DNS record and an API key, and those aren't mine to create. The real model has only run against a fake, because the key comes with a plan that is still being set up. I have no business numbers, since no published text has gone through it yet. Mobile performance is the weak spot: 66 to 71 on Lighthouse with simulated slow 4G. Docker isn't installed on the machine I built on, so I replayed the image steps instead of building the image, and I haven't run the security scan against a running copy.

When it's live I'll add the first real numbers: how many texts go out per week, and how often an approver sends one back.

*The company, the people, the industry and the colours in the screenshots are fictional. I rebuilt the demo data for them. The product, the interface and the workflow are real.*
