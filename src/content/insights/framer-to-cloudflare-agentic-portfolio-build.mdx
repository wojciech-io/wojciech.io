Most AI website rebuild stories are written like magic tricks: one prompt, one screenshot, one perfect deploy.

This was not that.

This was a working rebuild of my own portfolio and operator surface: the public `wojciech.io`, the app-style portfolio surface at `app.wojciech.io`, the work cards, CV, timeline, contact flow, article system, redirects, SEO plumbing, DNS cutover, and Cloudflare Pages deployment path.

The interesting part was not that AI wrote code. That is table stakes now.

The interesting part was the operating model: how Claude Code, Codex, Cloudflare Pages, GitHub, Astro, Playwright, terminal checks, and my own taste layer worked together without turning the site into a generic AI-generated landing page.

This is the breakdown.

---

## The goal

The goal was not "make the website look nicer."

The goal was to rebuild the site as a technical and editorial asset:

- move away from the old Framer-era structure;
- turn portfolio proof into a system, not a flat list of projects;
- connect the public site with the app-style portfolio surface;
- publish practical writing in a real article system;
- make deployments repeatable;
- make DNS and hosting easier to reason about;
- keep the visual system close to `app.wojciech.io`;
- make future changes agent-friendly without letting agents destroy the design language.

The old site was a web presence.

The new system needed to be a portfolio operating surface.

---

## The starting point

The previous public site had the usual legacy problems:

- it carried Framer-era assumptions about layout, animation, and content structure;
- the strongest proof was present, but not packaged cleanly;
- the AI/GTM work, shipped apps, operator profile, writing, and booking path were split across surfaces;
- the blog had one strong article and several older posts that did not belong in the new featured content strategy;
- the app surface had useful material, but the visual language needed to converge with the public site;
- deployment and DNS needed to move into a cleaner Cloudflare Pages setup.

The most important decision was to stop treating this as a design refresh.

It was a migration plus a productization effort.

---

## What we were building

The target architecture had two related surfaces:

```text
wojciech.io
  public positioning
  proof-led work system
  AI / GTM narrative
  insights articles
  contact and booking path
  SEO, RSS, sitemap, robots, redirects

app.wojciech.io
  app-style portfolio
  apps
  stack
  timeline
  CV
  contact
  compact profile UI
```

They did not need to be identical.

They needed to feel like the same person built them.

That meant shared decisions around:

- accent color;
- restrained typography;
- card radius;
- compact footer;
- toggle behavior;
- light/dark theme handling;
- proof-led information architecture;
- less marketing decoration, more operator-grade UI.

## Why not stay on Framer

Framer is useful when the primary problem is visual composition and publishing speed.

That was no longer the main problem.

The new site needed:

- versioned content;
- MDX articles;
- predictable redirects;
- sitemap and RSS generation;
- structured metadata;
- repeatable builds;
- deploy verification from terminal;
- agent-readable docs and code;
- easy diffs;
- a design system that could be patched safely.

Framer can ship a polished page, but it is not the control plane I wanted for an agent-assisted portfolio system.

The moment the site became a combination of content architecture, proof objects, launch checklist, DNS, redirects, articles, app references, and Cloudflare checks, code became the better surface.

---

## Why not Vercel

This was not an anti-Vercel decision.

Vercel is a strong default for many Next.js products, server-rendered apps, and teams already operating inside the Vercel ecosystem.

For this project, the constraints pointed elsewhere:

- the public site is static Astro, not a server-heavy app;
- there was no need for Vercel Functions as the main architecture;
- DNS and domain cutover were already central to the project;
- I wanted the custom domain, SSL, edge hosting, redirects, and analytics close together;
- the site needed simple static deployment, not platform complexity;
- I wanted to avoid a split-brain setup where DNS lives in one place and the serving platform lives somewhere else;
- `app.wojciech.io` also needed clean Cloudflare Pages verification.

Cloudflare Pages was the pragmatic fit.

The simpler architecture was:

```text
GitHub main
  -> npm run build
  -> dist/
  -> Cloudflare Pages project
  -> custom domain
  -> Cloudflare edge
```

That gave us fewer moving pieces for this use case.

---

## Why Cloudflare Pages

Cloudflare Pages fit the job because the site is mostly static and the launch problem was as much operational as visual.

The project needed:

- fast global static hosting;
- custom domain support;
- managed HTTPS;
- Cloudflare DNS alignment;
- simple deploy previews;
- direct deploys through `wrangler`;
- `_redirects` support;
- cache and header inspection from the terminal;
- Cloudflare Web Analytics without adding a heavy analytics layer;
- a way to verify that production was really serving the new build.

The decision was not about chasing infrastructure fashion.

It was about using the platform that matched the site:

- static site;
- code-first content;
- Cloudflare-managed domain;
- clear deployment artifact;
- low operational overhead.

## The deployment model

The deployment flow is intentionally boring:

```text
edit files
  -> npm run build
  -> git status
  -> git add
  -> git commit
  -> git push origin main
  -> npx wrangler pages deploy dist --project-name wojciech-io --branch main
  -> verify production domain
```

The important part is the final verification, not the deploy command.

After a deploy, we check:

```bash
curl -I https://wojciech.io/
curl -fsSL https://wojciech.io/insights/
curl -fsSL https://wojciech.io/rss.xml
```

And then we verify markers:

- does the public HTML contain the new article or CSS marker?
- does `server: cloudflare` appear?
- are `x-vercel-*` headers absent?
- does the custom domain serve the same thing as the Pages deployment?
- does the article route return `200`?
- did RSS and sitemap pick up the new content?

That is the difference between "I deployed it" and "the production site is actually serving the thing I think it is serving."

---

## DNS cutover

The DNS part mattered because the project had legacy surfaces and old assumptions.

The launch process was:

1. Keep the old production site live while building the new version.
2. Build the Astro site on staging.
3. Verify staging routes, redirects, SEO files, and article output.
4. Add the production custom domain to Cloudflare Pages.
5. Point the domain to the Cloudflare Pages project.
6. Confirm HTTPS certificate issuance.
7. Confirm `https://wojciech.io/` serves the new Astro site.
8. Re-run redirect, sitemap, RSS, robots, and article checks on production.

For `app.wojciech.io`, verification also included checking that the public domain was no longer leaking old platform headers and that Cloudflare was serving the expected build.

This became a repeated rule:

> Never trust a deploy URL alone. Verify the custom domain.

---

## Security and operational safeguards

This is not a bank-grade security architecture. It does not need to be.

But it does have a safer shape than a random dynamic website with exposed endpoints.

The security posture comes from simplicity:

- static Astro output;
- no database;
- no public admin panel;
- no app server in the request path;
- no exposed booking API on the static site;
- no secrets needed in the browser for core pages;
- external booking handled through Cal.com;
- production served behind Cloudflare;
- managed HTTPS;
- redirects and route behavior controlled in the repo;
- no heavyweight analytics script required for basic traffic visibility.

The contact page originally exposed a bad assumption: it tried to fetch `/api/cal/slots`, but the static site did not ship that API.

That was fixed by making the private scheduler the real path:

- no fake live availability;
- no red error state;
- no broken backend illusion;
- one clear "Open scheduler" CTA.

Security is often framed as adding more systems.

Here, the better move was removing an unnecessary system.

## The technical stack

Here is the real stack, separated by job.

### Site and content

**Astro**  
Static site framework. Used for page routing, layouts, content collections, MDX articles, static generation, sitemap output, and fast builds.

**Tailwind CSS**  
Used for layout, spacing, responsive behavior, and component styling.

**Design tokens**
The real design system lives in tokens: colors, surfaces, radius, borders, shadows, typography, and theme behavior.

**MDX content collections**  
Insights live in `src/content/insights/*.mdx`. This made the article system versioned, reviewable, and easy to deploy.

**RSS, sitemap, robots, canonical metadata, article schema**
These were part of the migration, not afterthoughts.

### Source control and deploy

**GitHub**
The source of truth. Every meaningful change lands as a commit.

**Cloudflare Pages**
Production hosting for `wojciech.io` and the app-style surface.

**Wrangler**
Used for direct terminal deploys when we wanted to push a known local `dist` build.

### AI and engineering loop

**Claude Code**  
Used for larger implementation batches: foundations, components, pages, article template, content migration, and broad feature work.

**Claude / Claude Design direction**  
Used for ideation and visual exploration, not as final source-of-truth code.

**Codex**  
Used for inspection, patches, conflict resolution, build verification, Playwright checks, deployment, Cloudflare validation, and tighter iteration after human critique.

**ChatGPT / GPT-5.5 strategy layer**  
Used for positioning, editorial structure, proof framing, and deciding what should not be migrated.

### QA and inspection

**Playwright**  
Used for browser checks: screenshots, desktop/mobile verification, overflow checks, theme toggle behavior, contact page state, and production sanity checks.

**curl**
Used for headers, status codes, and production HTML checks.

**rg**
Used for fast repo inspection: old copy, conflicting CSS, markers, dead references, and deployment proof.

## The sprint model

The work was organized like a product sprint, not like a single design session.

### Sprint 0: Decisions and setup

Outcome:

- old site audited;
- direction documented;
- hosting selected;
- repo created;
- Cloudflare Pages staging established;
- Framer kept live until launch readiness.

Human role:

- decide what the site should become;
- decide what should not be carried forward;
- approve Cloudflare as the deployment target.

### Sprint 1: Foundation and visual system

Claude Code handled:

- Tailwind setup;
- global tokens;
- layout primitives;
- reusable components;
- metadata and SEO primitives;
- content collection scaffolding.

Codex reviewed:

- project structure;
- accessibility baseline;
- SEO foundation;
- performance risks;
- whether the implementation matched the docs.

Human role:

- reject generic visual directions;
- choose the final direction;
- keep the system close to the app surface.

### Sprint 2: Core pages and proof

Claude Code handled:

- homepage;
- about;
- work;
- AI systems;
- proof clusters;
- testimonial and project cards.

Codex reviewed:

- responsive behavior;
- duplicate markup;
- component reuse;
- semantics;
- dead links.

Human role:

- choose proof hierarchy;
- validate which projects should be public;
- correct tone and positioning.

### Sprint 3: Content, SEO, and launch readiness

Claude Code handled:

- insights index;
- article template;
- migrated GTM Agent Starter Pack article;
- redirects;
- RSS;
- sitemap;
- robots;
- `llms.txt`;
- 404 page.

Codex handled:

- redirect checks;
- canonical checks;
- article route checks;
- build checks;
- production verification;
- Cloudflare deployment.

Human role:

- go / no-go for launch;
- decide what legacy content to keep, redirect, or retire.

### Sprint 4: Post-launch UI hardening

This is where a lot of visible quality came from.

The app surface went through several focused batches:

- header and profile layout;
- Stack cards;
- Timeline readability;
- CV accordion and role layout;
- Contact form and scheduler;
- light/dark toggle behavior;
- footer consistency;
- lime contrast in light mode.

This is also where the workflow became most honest.

Some AI output was directionally useful but visually wrong. The only way to fix that was screenshots, blunt critique, and focused patches.

## The agent roles

The cleanest split was this:

### Claude Code: implementation agent

Good for:

- larger build passes;
- setting up file structure;
- implementing page systems;
- following detailed docs;
- content migration;
- component scaffolding.

Weak when:

- the design critique is taste-heavy;
- several CSS layers have started conflicting;
- production verification requires careful terminal work.

### Codex: engineering QA and deploy agent

Good for:

- reading the repo state;
- making focused patches;
- resolving Git conflicts;
- rebasing against remote changes;
- running builds;
- Playwright QA;
- checking `curl` headers;
- verifying Cloudflare Pages deployments;
- confirming live markers on custom domains.

Weak when:

- asked to invent the entire visual direction without enough constraints.

### Human: product owner and taste layer

Good for:

- saying "this looks cheap";
- saying "this is too big";
- saying "this does not match Apps";
- deciding what proof is real;
- deciding what content should be retired;
- forcing the agents back toward the intended brand.

Weak when:

- trying to manually do all implementation work that agents can do faster.

The point was not to replace one role with another.

The point was to give each role the right job.

---

## The prompts were part of the system

The repo included explicit prompts for agent handoff:

- Claude Code kickoff;
- Claude design exploration;
- Codex SEO foundation review;
- Codex responsive QA.

That kept the agents from freewheeling.

Each prompt had a narrow job:

- inspect docs before writing code;
- propose a sprint plan;
- review SEO foundations;
- review responsive behavior;
- identify file-level issues;
- avoid rewriting positioning unless asked.

Without this, every agent tries to be designer, engineer, strategist, copywriter, release manager, and QA at once.

That is how you get a confident mess.

## The testing model

The test model combined automated checks, browser automation, and manual visual review.

### Automated checks

The baseline check was:

```bash
npm run build
```

That verified:

- Astro content collections;
- MDX parsing;
- static route generation;
- sitemap generation;
- RSS generation;
- TypeScript / framework-level build errors.

For article work, the build had to generate:

```text
/insights/framer-to-cloudflare-agentic-portfolio-build/
/insights/
/rss.xml
/sitemap-index.xml
```

### Browser automation

Playwright was used to check:

- page titles;
- article `h1`;
- presence of links in `/insights/`;
- desktop overflow;
- mobile overflow;
- theme toggle state;
- Contact scheduler state;
- footer link count;
- live production behavior.

Example checks:

```text
desktop overflow: 0
mobile overflow: 0
theme: light -> dark
article route: 200
Cloudflare headers present
Vercel headers absent
```

### Terminal verification

`curl` checked production reality:

```bash
curl -I https://wojciech.io/
curl -I https://wojciech.io/insights/framer-to-cloudflare-agentic-portfolio-build/
```

`rg` checked whether the deployed HTML contained the expected markers:

```bash
curl -fsSL https://wojciech.io/insights/ | rg "From Framer to Cloudflare"
curl -fsSL https://wojciech.io/rss.xml | rg "From Framer to Cloudflare"
```

### Manual review

Manual review caught what automated checks could not:

- typography felt too large;
- a white panel did not belong in Timeline;
- CV felt like a PDF import;
- Contact felt cheaper than the rest of the site;
- light-mode lime was too harsh;
- Stack cards lost the visual quality of the app surface.

Frontend QA is not only whether the route loads.

It is whether the page feels like the same product.

## What went wrong

Several things went wrong, and they were useful.

### 1. The accent color broke in light mode

The brand lime `#ebff00` works as a CTA background.

It does not work everywhere as text or icon color on a pale background.

The fix was semantic separation:

- bright lime for CTA backgrounds;
- darker olive-lime for text, icons, links, and subtle accent work in light mode;
- brighter lime preserved in dark mode where contrast supports it.

### 2. Sections drifted into different design systems

Apps and Contact looked coherent.

Stack, Timeline, and CV started to feel like separate products.

The fix was to normalize:

- container widths;
- radius;
- border weight;
- heading scale;
- chip styling;
- footer behavior;
- toggle behavior;
- light/dark token use.

### 3. CV initially looked like a PDF import

The CV needed information architecture, not decoration.

The better model was:

- roles as accordion sections;
- responsibilities and outcomes inside each role;
- tools and setup widgets compressed into a secondary area;
- roles closed by default so the page does not become endless.

### 4. Contact exposed backend assumptions

The static site did not actually have a live `/api/cal/slots` endpoint.

The UI was pretending it did, which created a red error state in the booking card.

The fix was to make the private scheduler the real path:

- no fake live availability;
- no red "fallback" copy;
- one clear scheduler CTA;
- calm status copy.

### 5. Deploy verification mattered more than expected

At several points, the important question was not "is the code right?"

It was:

- which origin is the domain actually serving?
- are Cloudflare headers present?
- are old platform headers gone?
- did the custom domain receive the new build?
- is production HTML carrying the marker we expect?

This is why browser checks and `curl` checks became part of the workflow.

The real output was not just a redesigned website.

- Insights became a real MDX article system;
- the GTM Agent Starter Pack was migrated into the new article template;

- SEO files, RSS, sitemap, robots, redirects, and schema became part of the codebase;
- contact and booking became calmer and more product-like;
- light/dark theming became more consistent;
- footer and toggle patterns converged across surfaces;
- deploys became repeatable;
- production verification became part of the workflow.

This is a real use case because it combines things most AI demos avoid:

- legacy site migration;

- UI taste problems;
- design-system drift;

## The agentic build pattern

This is the pattern I would reuse.

### 1. Start with docs, not code

Before opening the editor, define:

- what the site is for;
- what the old site should keep;
- what should be retired;
- what the design direction is;
- what proof needs to be shown;
- what launch checks matter.

### 2. Split agents by job

Do not ask every model to do everything.

Use:

- Claude Code for large implementation batches;
- Codex for engineering review, QA, conflicts, deploys, and patches;
- GPT strategy layer for positioning and editorial structure;
- the human for taste, judgment, and go/no-go decisions.

### 3. Work in batches

Do not ask for "make the site better."

Ask for:

- fix the contact scheduler state;
- normalize Stack card radius and width;
- make Timeline consistent with Apps;
- close CV roles by default;
- verify Cloudflare headers;
- check RSS contains the article.

Small batches produce better agent work.

### 4. Verify visually

No frontend work is done until screenshots say it is done.

A build can pass while the product looks wrong.

### 5. Verify production

A deploy URL is not enough.

The custom domain has to serve the right HTML, from the right platform, with the right headers.

### 6. Keep critique concrete

The best human feedback in this process was direct:

- too large;
- too gray;
- too cheap;
- wrong direction;
- not coherent with Apps;
- looks like imported PDF;
- white slab does not belong here.

The more concrete the critique, the better the patch.

## The short version

We did not build this with one AI tool.

We built it with an operating loop:

- Framer as the old surface;
- Astro as the new public architecture;
- Tailwind and tokens as the UI system;
- MDX as the article layer;
- GitHub as the source of truth;
- Claude Code as the larger implementation agent;
- Codex as the engineering, QA, and deployment agent;
- Playwright as visual verification;
- Cloudflare Pages as production;
- Wrangler as deploy tooling;
- `curl` and `rg` as boring but essential inspection tools;
- human judgment as the thing that kept the result from becoming generic.

That last one is the real stack.

Agentic building does not remove taste, judgment, or ownership.

It punishes you faster when you do not have them.
