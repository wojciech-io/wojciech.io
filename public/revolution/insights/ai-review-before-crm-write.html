Put a review step before an AI-driven CRM update

An AI draft is cheap. A wrong CRM record is not. Put one person between the two, and give them what they need to say yes.

Wojciech Luszczynski2 min read

Start with one job you can undo

Pick a point where someone already checks the work. An inbound enquiry is a good one. The first version proposes a qualification summary, the missing questions and a reply. The reviewer sees the original request and the extracted facts next to the draft.

Keep what was said apart from what the model inferred

A buyer who says “we are comparing vendors” supports a buying-stage note. It says nothing about budget. If timing is missing, I leave the field empty and ask. Every field keeps a stable reference to its evidence, so a second reviewer can check it later.

Edit the draft and the approval is gone.

Approve one version and one action

Approval is tied to the reviewed revision and its destination. Edit the proposal and it becomes a new revision that needs a new approval. When the app writes to a CRM, I check permissions at the write step and use an idempotency key, so a repeated request cannot create a second record. The approval and its result are logged.

Test in layers

Scripted tests cover routing, missing fields and permissions. Separate model checks cover grounded extraction and ambiguous input. For a pilot I would measure draft acceptance, edits per accepted draft, unsupported field claims and time to the first useful response.

A local workflow test shows the routing works. Only a reviewed pilot can show whether it saves time.

What the reviewer needs

The facts, the gaps and the exact action they are approving. If one of the three is missing, the review is a formality.
